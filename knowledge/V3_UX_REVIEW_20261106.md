## Why moving the models remains open

The current relation is `model → engine`, named `is-hosted-on`. The topology
layout uses source/target direction. The installed derived-state function follows
outgoing dependencies and accepts only `componentTypes`; it has no direction
override. Reversing the edge would place the engine above its model but remove
that model's inherited engine health under this implementation. Native model
checks, such as vLLM's latency checks, are a separate source of health.

The [native mapping schema](https://documentation.suse.com/external-tree/en-us/cloudnative/suse-observability/latest/en/setup/custom-integrations/otelmappings/schemas-ref.html)
provides relation source, target, type and dependency type, with no independent
visual rank/direction or layer assignment. The earlier [S2 spike](SPIKE_V3_COMPONENT_MODEL.md)
also demonstrated that domain/layer output keys are discarded. The
[derived-state contract](https://documentation.suse.com/external-tree/en-us/cloudnative/suse-observability/latest/en/setup/custom-integrations/monitors/derived-state-monitors.html)
does not supply a reverse-traversal option.

The built-in health aggregator accepts `title`, `query` and `urnTemplate`; it
maps source tags to a target identifier. It does not automatically fan one engine's
state out to all its model neighbors. The incorrect argument examples in
[the monitor guide](MONITOR_CREATION_GUIDE.md#advanced-patterns) have been corrected
using the installed function definitions.

Meeting both requirements needs supported layout control independent of health,
or a separate health-propagation implementation. No duplicate opposite edges,
unsupported mapping fields or fabricated healthy states were added. Browser
topology screenshots are excluded: the review harness authenticated HTTP but not
the topology WebSocket, so a loading canvas is not evidence of a product defect.
